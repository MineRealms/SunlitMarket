# 货币模型与交易不变量（定稿 v2）

> 本文**取代** `ECONOMY_STAGE_LOCKS.md` 的 §0 / §2 / §4 / §5。
> 其余章节（§3 衰减、§6 货单类型、§7 接受仓、§8 期货、§11 JSON）继续有效，但以本文的账户与不变量为准。

## 0. 先承认三个错误

| 原文 | 错在哪 |
|---|---|
| 「钱只能由当铺的现金创造」 | **事实错误**。`Currency.settle()` 在 `moneyDelta > 0` 时直接 `mint()` 硬币进背包，没有对手方。当铺今天就是一台印钞机。 |
| 「当铺的现金只能由玩家消费补充」 | 这是**转账**，不是发行。玩家付钱给当铺，M 不变。 |
| `refill = 0.02 × cash` | 复利型外部发行，无赛季上限。这是把封闭系统偷偷改成开放系统，而且没有刹车。 |

修正后的立场：

> **货币总量 M 只能由「发行准备金」增加，只能由「当铺买入 + 手续费 + 期货手续费」减少。
> 当铺的现金 C 是缓冲池，不是货币来源。**

## 1. 事实基础（不是假设，是实测）

在写模型之前先把现状钉死，否则后面全是空谈。

### 1.1 货币是**物品**，不是数字

`currency/Currency.java`：
- 面额表 `spur=1 … prismatic_coin=16777216`
- 装了 Create: Numismatics 时读银行余额，否则数背包里的硬币
- **所有收支都走同一个方法** `settle(player, source, target, item, count, moneyDelta)`
  - `moneyDelta > 0` → `mint()` 造币
  - `moneyDelta < 0` → 从背包扣币，多扣的再 `mint()` 找零

**这带来一个非常有用的性质**：全服唯一的两处铸造/销毁点都在 `settle()` 里。
只要在 `mint()` 和扣币分支各记一笔账，就能得到**精确的货币总量**
（`M = Σminted − Σburned`），与硬币散落在谁家箱子里无关。

这是整个方案能被验证的前提 —— 否则「货币总量」只是口号。

### 1.2 配方数据已经够用了（今天刚导出的 v2）

`H:/Tools/sunlit_jei_recipes.json`（186 MB，`version: 2`，2026-11-02 导出）实测：

| 项 | 数量 | 用途 |
|---|---:|---|
| 分类总数 | 172 | — |
| **`gtceu:*` 机器分类** | **108** | 装配线/组装机/化学反应釜/电弧炉…全都在 |
| 配方总数 | ~11.6 万 | — |
| **`gtceu:arc_furnace_recycling`** | **4,351 条** | **这就是残值表**，不用自己推 |
| 物品产出总数 | 21,137 | — |
| 有回收配方的物品 | 4,351 | 占 21%，但覆盖的正是 GT 材料/方块（钱都在这） |
| 每条配方带 `gt` 块 | 是 | `duration / eut / tier / tier_index / total_eu` 全有 |

结论：**「GT 配方图算不出残值」这个担心不成立** —— GT 自己就有电弧炉回收配方，
残值 = 回收产物按价格求和，这是官方定义，不是我们的猜测。

### 1.3 FTBQ 任务图可以当「经济需求」的代理

`ftb_quests_map.json` 实测：30 章 / 1,173 任务 / 1,341 任务条目，其中 1,215 条是 `item` 类型。
每章有 `group_index + order_index`，每任务有 `dependencies`。

这正好补上「电压等级 ≠ 经济价值」的缺口：**任务图编码的是「策划认为玩家什么时候该有它」**，
比 `tier_index` 更接近真实需求。

## 2. 账户模型

三个账户，缺一不可：

```
W  玩家钱包      = Σ 玩家背包硬币 + Σ 银行余额
C  当铺运营现金   = 当铺自己的硬币储备（真实物品，可被看见、可被抢）
R  发行准备金     = 系统账户，只进不出地记账（不对应任何实体硬币）
```

```
M = W + C + R            // 全系统货币总量
ΔM = mint − burn         // 只有这两项能改变 M
```

### 2.1 每笔交易的账户变化

| 事件 | W | C | R | M |
|---|---|---|---|---|
| 玩家买货 | −x | +x | | 0 |
| 当铺收货 | +y | −y | | 0 |
| **新玩家启动金** | +z | | −z | 0 |
| **赛季发行** | | +z | −z | 0 |
| NPC 顾客向玩家买货 | +y | | −y | 0 |
| 手续费 / 期货亏损 | −f | | | **−f** |
| 期货盈利（对家是玩家） | ± | | | 0 |

关键点：**发行不是「凭空造钱」，是「准备金 → 某个账户」的转移**。
准备金是有限的，所以 M 的上界是有限的；准备金为 0 时系统彻底封闭。

### 2.2 当铺现金必须是**真实硬币**

如果 C 只是一个数字，玩家永远无法判断当铺"有没有钱"，也就无法形成"抢购/惜售"的博弈。
建议 C 就是一个箱子（或一组箱子），玩家能看见、能抢（犯罪系统已经在了），
并且当铺收货时**从箱子里掏硬币给玩家**，而不是 mint。

这样「当铺没钱了」是一个玩家能亲眼看到、能利用、能抢劫的状态 —— 比任何 UI 数字都有说服力。

## 3. 发行规则（回答"钱从哪来、发多少"）

### 3.1 初始

```
R0 = max(20000, N_players × 5000)          // 赛季发行准备金
C0 = N_players × 20000                     // 当铺初始现金
新玩家启动金 = 2000 spur（一次性，记在玩家 NBT）
```

启动金从 R 出，不从 C 出 —— 否则新玩家一进服就在稀释老玩家的现金池。

### 3.2 赛季上限（硬约束）

```
Σ refill ≤ R_season = 3 × R0
refill_d = min(0.02 × C_d, (R_season − Σrefill) / 剩余天数, r_max)
```

三条同时生效，取最小。`r_max` 是单日绝对上限（建议 = 5% × M）。
赛季末 R 用尽 → 系统完全封闭 → 只剩手续费销毁，货币开始通缩。
**这是设计意图，不是 bug**：通缩让赛季末的钱更值钱，鼓励囤币而不是囤货。

### 3.3 现金枯竭时的降级（回答"现金不足怎么办"）

绝不允许自动增发补足。三级降级：

| C 占 C0 | 行为 |
|---|---|
| > 20% | 正常 |
| 5%–20% | 只收「高需求」货单，收货价 ×0.8，UI 显示「当铺现金紧张」 |
| < 5% | 全部停收，只卖不收，UI 显示「当铺今日已无现金」 |
| = 0 | 同上，且允许玩家**抢劫**（犯罪系统的天然出口） |

## 4. 交易不变量（I1–I7，全部可断言）

写成 `CoreSelfTest` 级别的启动检查 + 每笔交易的运行期检查：

```
I1  守恒   M_after − M_before = mint − burn        （逐笔，误差必须为 0）
I2  残值   sell(item) ≤ salvage(item) × 0.6
I3  无环   不存在「买 → 加工 → 卖」净收益为正的配方路径
I4  预算   Σ当日回收 ≤ C_available
I5  额度   Σ当日回收(玩家,物品) ≤ quota(玩家,物品)
I6  阶段   item.techTier − player.techTier ≥ 3 → 拒收
I7  原子   物品销毁与记账同 tick 完成；任一失败则全部回滚
```

I2/I3 的输入全部来自 §1.2 的导出数据，不需要人工定价。
I1 只需要在 `Currency.mint()` 和扣币分支各加一个回调。

## 5. 残值：直接用 GT 的回收配方

```
salvage(item) = Σ over arc_furnace_recycling(item) outputs:
                    count × unitValue(output)
unitValue(x)  = 已知材料价（下方表） 或 递归 salvage(x) × 0.5（深度 ≤ 3）
```

- 回收配方是 GT 官方定义的"拆解价值"，比任何手工定价都权威
- 副产物、概率产物按 **期望值** 计入（`count × probability`）
- 没有回收配方的物品（Boss 掉落、结构战利品）走「稀缺品」分支：允许高价，但额度极小
- 递归深度限制 3 层，防止环

**注意**：`arc_furnace_recycling` 里有大量 NBT 变体（转子带 `GT.PartStats.Material`），
匹配时必须按 `(itemId, NBT 的 material 字段)` 归一化，否则覆盖率会掉一半。

## 6. 阶段：拆成两个维度

用户指出的问题完全正确 —— 电压等级不等于经济价值。拆成：

```
techTier(item)   = min over recipes producing item of gt.tier_index
                    （做出来需要的最低电压，机器方块取 block 的 tier_index）

demandTier(item) = 由 FTBQ 任务图推出：
                    任务图深度 → 1..10 级
                    是任务 reward → 降 2 级（游戏本来就白送）
                    在「收藏」章节 → 降 1 级（非刚需）
```

卖价公式改为：

```
sell = base × F_tech(Δtech) × F_demand(demand) × F_stock(S) × F_quota(n)
```

其中 **`F_tech` 只影响「能不能收」，`F_demand` 影响「值多少」**：

| Δtech = player − item | F_tech |
|---|---|
| ≤ 0 | 1.00 |
| 1 | 0.60 |
| 2 | 0.25 |
| ≥ 3 | 0.00（拒收） |

这样 LuV 玩家卖钢锭仍然可以（钢的 Δtech 可能是 5，会被拒收）——
等等，这正好暴露了问题：**钢对 LuV 玩家确实是"过时"的**。

所以真正的解法是 `F_demand` 兜底：钢的 `demandTier` 很高（任务图里到处都要钢），
当 `F_tech → 0` 时改判为「材料级回收」：**按残值收，不按成品价收**。
即：

```
if F_tech == 0:  sell = salvage(item) × 0.5 × F_demand   // 当废料收，永远有出口
else:            sell = base × F_tech × F_demand × F_stock
```

**这就是"低级产线不会失去经济意义"的答案**：它退化成废料回收，
钱少但不会变成 0，也不会成为印钞口。

## 7. 统一预算调度器（合并 quota + budget + 库存压力）

三层限制互相打架的根源是它们各自独立判断。合并成一个状态机：

```
submit(player, item, count):
  1  offer.accept ∈ {TRADE, SELL_ONLY} ?            否 → REJECT_NOT_BUYING
  2  techTier 检查通过 ?                            否 → REJECT_TIER
  3  经济日历：今天是 server_day（持久化）          否 → 跨日则先滚动
  4  quota 剩余 > 0 ?                               否 → REJECT_QUOTA
  5  C_available ≥ 本次金额 ?                       否 → REJECT_NO_CASH
  6  金额 = min(quote(count), quota剩余金额, C_available)
  7  原子：销毁物品 + 从 C 掏硬币 + 记账 + 更新库存
```

**经济日历必须持久化**（`MarketData` 里存 `server_day` + 当日累计），
不能用 `System.currentTimeMillis() / 86400000`。理由：
服务器重启、时区、夏令时、手动改时间都会制造跨日漏洞。
建议：`server_day` 只随 `Level.getDayTime()` 推进，且每笔交易后落盘。

## 8. 期货：庄家不接盘

原方案没写清楚一件事：**期货的对手方是谁**。

- 如果是当铺（庄家接盘）→ 当铺亏钱 = 印钞，等于把无限生产套利换成无限金融套利
- 如果是玩家对玩家 → M 不变，只是财富重分配，安全

**结论：期货必须是玩家对玩家，庄家只收手续费（销毁），永不持仓。**
没有对手盘时挂单不成交，而不是庄家吃单。

配套限制：
- 全额保证金，先不做杠杆
- 单玩家持仓上限 = f(其净资产)，防止巨鲸
- 结算用 TWAP（最近 N 个采样均值），且**只统计真实成交**，挂单不参与
- 单玩家对指数的贡献上限（例如 ≤ 5% 权重）
- 指数异常波动熔断：单日 ±25% 触发暂停并公告

## 9. 监管层（Layer 4）

### 9.1 Economic Ledger
每笔交易一行 JSONL，字段按用户给的模板，补三个：
```
"mint_delta": 0,           // 本笔铸造/销毁了多少
"cash_after": 9200.0,      // 当铺现金
"M_after": 214000.0        // 全服货币总量（由 mint/burn 累计得出）
```
落盘 `config/sunlitmarket/ledger/YYYY-MM-DD.jsonl`，只追加，不修改。

### 9.2 Circuit Breaker
| 触发 | 动作 |
|---|---|
| C < 5% C0 | 停收 |
| 某物品 1 小时成交量 > 3σ | 该货单冻结 30 分钟 |
| 审计发现负收益环 | 相关货单直接下架 |
| 单日 mint > 2 × 预算 | 暂停发行，告警 |
| 单玩家单日回收 > 10 × 中位数 | 人工复核 |

### 9.3 审计器（`MarketEconomyAuditor`，独立包 `audit/`）
不混进货单加载代码。三种检查：
1. **Direct**：单配方 `V_out > V_in + 处理成本`
2. **Cyclic**：配方图上找正收益环（Bellman-Ford 变体，`V` 取 −log 做加法）
3. **Multi-output**：主产品亏损但副产物回收价覆盖，整条链仍为正

多输入配方不是"边"而是"超边"，所以用 **LP 对偶** 而不是最短路：
```
max  Σ p_j q_j − Σ p_i q_i
s.t. 所有在售物品的 buy/sell 价格固定
```
实际实现可以用迭代法近似（`p ← min(p, min over producers)`，迭代到收敛），
比 LP 简单得多，且对 GT 这种规模足够。

## 10. 四个必须现在定稿的问题（我的答案）

### Q1 初始货币从哪来？
**发行准备金 R**，一次性注入：`R0 = max(20000, N×5000)`。新玩家 2000 spur 从 R 出。

### Q2 每赛季最多发行多少？
`R_season = 3 × R0`，日增发三条件取最小（见 §3.2）。赛季末归零后系统封闭、开始通缩。

### Q3 当铺现金不足怎么办？
三级降级（§3.3），**绝不自动增发**，最低一级允许抢劫。

### Q4 玩家之间转账是否允许？
**允许**（钱是物品，禁止也没意义），但：
- 收 5% 转账税（销毁），因为转账是 RMT 和洗额度的入口
- 每日额度按**钱包**记，不按账号 → 小号问题用「额度 × min(1, 在线时长/2h)」加权
- 单人/小服可以整条关掉（配置项）

## 11. 修订后的实施顺序

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| **S0** | Ledger + `mint/burn` 回调 + 货币总量统计 | 没有它，后面所有约束都无法验证 |
| **S1** | 三账户模型 + 当铺真实硬币储备 + 发行准备金 | 货币模型的地基 |
| **S2** | 残值表（`arc_furnace_recycling`）+ 价格表落盘 | 审计器和报价都依赖它 |
| **S3** | `MarketEconomyAuditor`（Direct / Cyclic / Multi-output） | **必须在开放回收之前**，否则先开后补 |
| **S4** | `BuybackBudgetManager` + 经济日历 + 原子交易 | 统一三层限制 |
| **S5** | techTier / demandTier + 废料兜底 | 阶段锁 |
| **S6** | 接受仓（物品 + 流体，禁止自动化） | 玩家能摸到的出口 |
| **S7** | 能源 / 源质 / 魔力（只给信誉，不给钱） | 观察一周再决定 |
| **S8** | 期货（P2P，庄家不接盘，TWAP） | 最后做，且不依赖它发钱 |
| **S9** | 日终 JSON 导出 | 数据分析 |

用户建议把审计提到 P0 是对的，我进一步提前到 S3（在预算管理器之前），
因为**审计器决定了哪些物品允许进回收白名单**，而预算管理器只决定"收多少"。
顺序错了会出现"预算正确但白名单有毒"。

## 12. 一句话总结

> 玩家可以拥有无限生产力，但无限生产力只能兑换成**有限的、按日结算的**购买力；
> 而购买力的总量由准备金封顶，由手续费通缩。
> 工业层、商品层、货币层、监管层互不越界 —— GT 改配方不会打穿货币，加模组不会打穿市场。
